3.1

Arsitektur Layer

Sistem menggunakan arsitektur empat layer yang mengadaptasi Clean Architecture ke dalam konteks Laravel MVC. Setiap layer memiliki tanggung jawab yang jelas dan dependency hanya mengalir ke bawah (layer atas bergantung pada layer bawah, tidak sebaliknya).

Presentation Layer
Blade Views, Chart.js, Routes, Middleware

Menerima input pengguna dan menampilkan output. Tidak berisi business logic.

Blade Templates AdminLTE 4 Chart.js Routes Form Requests
Application Layer
Controllers, Services

Mengorkestrasikan alur proses. Controller menerima request, memanggil Service, mengembalikan response. Service berisi seluruh business logic.

Controllers TracerAnalysisService StatisticsService NarrativeService ReportGeneratorService ExcelReaderService
Domain Layer
Models, Repository Interfaces, Config

Mendefinisikan entitas bisnis dan kontrak akses data. Tidak bergantung pada framework atau database.

TracerStudy AnalysisResult Report Repository Interfaces Parameter Config
Infrastructure Layer
Eloquent Repositories, PhpSpreadsheet, PHPWord, MySQL

Implementasi konkret akses data, file I/O, dan library pihak ketiga.

Eloquent Repositories PhpSpreadsheet PHPWord MySQL Laravel Filesystem

Alasan Teknis

  • Controller tipis: Controller hanya menerima request tervalidasi (Form Request), memanggil Service, dan mengembalikan response/view. Tidak ada query, kalkulasi, atau logika kondisional di Controller.
  • Service Layer: Seluruh business logic (pengolahan statistik, generate narasi, generate laporan) berada di Service. Ini memungkinkan reuse logic antara web controller dan command-line jika diperlukan di masa depan.
  • Repository Pattern: Akses data melalui interface, implementasi menggunakan Eloquent. Jika di masa depan perlu mengganti ORM atau database, cukup ganti implementasi repository tanpa mengubah Service.
  • Dependency Injection: Seluruh Service dan Repository di-inject melalui Laravel Service Container. Tidak ada instansiasi manual (new Service()) di Controller.
3.2

Design Patterns

Repository Pattern

Abstraksi akses data melalui interface. Controller dan Service tidak tahu apakah data berasal dari Eloquent, Query Builder, atau cache. Memudahkan testing dengan mock.

Service Layer

Mengenkapsulasi business logic dalam class yang fokus pada satu domain. Menghindari fat controller dan memungkinkan reuse logic di berbagai entry point.

Strategy Pattern

Setiap parameter analisis memiliki strategi pengolahan berbeda (frequency, mean, sum, index, display). Strategi di-resolve berdasarkan konfigurasi parameter.

Config-Driven Processing

Mapping 13 parameter (kolom, tipe statistik, kategori, chart) didefinisikan dalam config file, bukan hardcoded di Service. Menambah atau mengubah parameter cukup edit config.

Form Request Validation

Validasi input dipisahkan dari Controller ke Form Request class, sesuai Laravel convention dan SRP (Single Responsibility Principle).

View Composer / Component

Blade component reusable untuk card parameter, chart wrapper, dan tabel statistik. Menghindari duplikasi markup di 13 parameter card.

3.3

Request Lifecycle: Upload & Analisis

Alur paling kritis dalam sistem adalah proses upload file Excel hingga hasil analisis tersimpan di database. Berikut lifecycle-nya:

01 Browser Form upload .xlsx + meta info
→
02 Form Request Validasi file, meta fields
→
03 Controller Panggil TracerAnalysisService
→
04 ExcelReaderService Baca sheet, extract array data
05 StatisticsService Hitung per parameter via Strategy
→
06 NarrativeService Generate narasi per parameter
→
07 Repository Simpan ke analysis_results
→
08 Cleanup Hapus file Excel temp

Request Lifecycle: Generate Laporan

01 Controller Panggil ReportGeneratorService
→
02 Repository Ambil analysis_results + meta
→
03 ReportGenerator Susun dokumen Word via PHPWord
→
04 Storage Simpan .docx, catat di reports

3.8

Config-Driven Parameter Processing

Seluruh definisi parameter disimpan di config/tracer.php sebagai array asosiatif. Ini memungkinkan penambahan atau modifikasi parameter tanpa mengubah kode Service.

KeyTipeContohKeterangan
numberint1Nomor urut parameter
namestring'Status Setelah Lulus'Nama parameter
groupstring'status_alumni'Grup parameter
columnstring'M'Kolom Excel (letter)
f_codestring'f8'Field code DIKTI
statistic_typestring'frequency'frequency | mean | median | sum | index | display
categoriesarray[1 => 'Bekerja', ...]Mapping nilai → label (null jika tidak kategorikal)
chart_typestring|null'pie'pie | bar | grouped_bar | null
range_rulesarray|null[['<', 6, '< 6 bln'], ...]Aturan range untuk COUNTIF berbasis range (parameter #2, #8)

Keuntungan: StatisticsService hanya perlu membaca config, loop parameter, dan memanggil metode hitung yang sesuai berdasarkan statistic_type. Tidak ada if parameter == 1 then ... di dalam Service.

3.9

Dependency Injection & Service Provider

Seluruh binding Repository Interface → Implementasi dilakukan di AppServiceProvider::register(). Service di-inject via constructor injection di Controller.

InterfaceBound To
TracerStudyRepositoryInterfaceEloquentTracerStudyRepository
AnalysisResultRepositoryInterfaceEloquentAnalysisResultRepository
ReportRepositoryInterfaceEloquentReportRepository

Service tidak memerlukan binding eksplisit karena tidak menggunakan interface — mereka adalah concrete class yang langsung di-resolve oleh Laravel container melalui auto-resolution. Jika di masa depan ada kebutuhan swap implementasi (misalnya ReportGenerator untuk format lain), barulah dibuatkan interface.

3.10

Keputusan Arsitektural

KeputusanAlasanAlternatif yang Ditolak
Synchronous processing (bukan queue) File Excel ≤ 5.000 baris, proses < 30 detik. Queue menambah kompleksitas (Redis/Supervisor) tanpa manfaat signifikan untuk skala ini. Laravel Queue + Job: overhead setup untuk single-user app
JSON column di analysis_results Setiap parameter menghasilkan struktur data berbeda (frekuensi, mean, tabel teks). JSON column fleksibel tanpa perlu tabel tambahan per tipe. Tabel terpisah per tipe statistik: terlalu banyak tabel untuk 13 parameter
Config file untuk parameter mapping Parameter jarang berubah, tidak perlu CRUD via UI. Config file lebih simple dan versionable via Git. Tabel parameters di database: over-engineering untuk 13 parameter tetap
Blade + Chart.js (bukan SPA) Aplikasi bersifat read-heavy dengan sedikit interaksi. Server-side rendering via Blade lebih simple daripada SPA (Vue/React) dan sesuai dengan AdminLTE. Livewire: dependensi tambahan. Inertia+Vue: kompleksitas build pipeline
Hapus Excel setelah analisis Data mentah tidak diperlukan setelah analisis. Mengurangi storage dan risiko penyimpanan data pribadi mahasiswa (NIM, nama, NIK). Simpan permanen: risiko keamanan data pribadi
Tanpa middleware auth Single-user app yang diakses pribadi. Tidak ada tabel users, tidak ada session auth. Menyederhanakan arsitektur secara signifikan. Laravel Breeze/Fortify: unnecessary untuk single user
